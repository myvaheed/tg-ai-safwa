находки первого аудита и проверенные предложения второго. Выполненный пункт помечен **Сделано**

0 обнаруженных циклов и нарушений. Четыре ошибки исполнения ниже дополнительно воспроизведены

## 1. P1 — Закрыть обход SQL-ограничения

**Факт.** [scan_statement](../src/tg_agent_shell/ai/sql.py) собирает имена CTE в общее множество,
не учитывая область видимости. Следующий запрос через настоящий ReadOnlyQueryRunner вернул
количество строк запрещённой таблицы при allowlist, содержащем только ai_public:

```sql
SELECT count(*) AS n
FROM private_rows
WHERE EXISTS (
  WITH private_rows AS (SELECT 1 AS id)
  SELECT id FROM private_rows
)
```

Это другой обход, чем исправленный в POLISHING 1.4 псевдо-CTE внутри строкового литерала.
Authorizer допускает чтение без имени столбца, поэтому ошибку первого слоя не останавливает.
Валидатор Requests также принимает обращение к внешней таблице через этот приём; Requests
исполняют SQL обычной сессией, без authorizer. Граница доказательства для read-only runner —
получение количества строк; чтение текстовых полей или запись этим воспроизведением не доказаны.

**Изменение.** Корректно разбирать источники данных и области видимости CTE. Выбрать минимальный
разбор, который покрывает поддерживаемый диалект, и убрать заменённые эвристики. Не расширять
набор независимых регулярных выражений вокруг отсутствующей проверки области видимости.
Согласовать валидатор и исполнение для всех потребителей, включая Requests и поиск родителя Card.

**Готово:** запрос выше и варианты с вложенностью, совпадающими именами и квалифицированными
источниками отвергаются; законные CTE, recursive CTE, count по доступным views и строковые
литералы сохраняют поведение. Проверяются реальные чтения с разными allowlist, а не только текст
ошибки валидатора. Основание: AG-READ-027, SR-SQL-004, SR-SQL-005.

**Сделано.** [scan_statement](../src/tg_agent_shell/ai/sql.py) разбирает области видимости: стек
уровней скобок, CTE объявлен на своём уровне и недоступен снаружи, источники резолвятся после
обхода против уровней, открытых в точке ссылки — это и есть правило SQLite. Заменённые
эвристики по глубине скобок удалены, новых регулярных выражений нет; `validated_read` отдаёт
statement и прочитанные views одному вызову. Проверки в [test_ai_sql.py](../tests/test_ai_sql.py):
запрос выше, вложенность, совпадающие имена и квалифицированный источник отвергаются через
настоящий `ReadOnlyQueryRunner`; законные, recursive и вложенные CTE читаются; один и тот же
запрос отвечен или отвергнут по списку самого читателя.

## 2. P1 — Завершать отменённый фоновый ход целиком

**Факт.** [TurnManager.cancel](../src/tg_agent_shell/turn/manager.py) инвалидирует фоновый ход,
но не отменяет его задачу. [CueRuntime.speak](../src/tg_agent_shell/cues/runtime.py) проверяет
актуальность после root.handle, когда тот уже мог создать review и очередь.
Воспроизведение: задержать ответ провайдера, имитировать приход владельца, разрешить ответу
продолжиться. Сообщение не доставляется, но остаются одно невидимое предложение и одна очередь;
следующий can_speak возвращает False.

**Изменение.** Сделать принадлежность фоновой работы конкретному ходу явной. Отмена должна
останавливать его выполнение и завершать только его незаконченные review и сессии. Проверять
актуальность перед публикацией и применением изменений. Завершение старого хода не должно
освобождать lease, уже переданный новому; отмена одного хода не должна убивать постоянный poll.

**Готово:** тест с настоящими RootSession, ProposalStore и CueRuntime, заменённым провайдером
и управляемыми событиями воспроизводит гонку; после исправления невидимых review и claims нет,
Cue остаётся в очереди и доставляется позже. Отдельно проверены отмена перед autoapproval,
приход владельца во время подготовки и завершение старой работы после получения нового lease.
Основание: AG-TURN-015, AG-CUE-029, AG-POLL-030, SC-FAIL-005.

**Сделано.** `BackgroundWork` несёт revision — имя своего lease — и задачу, которая эту работу
делает. `TurnManager.start_background` создаёт её рядом с `cancel()`, поэтому отменяется ход, а не
poll; `end_background(revision)` отдаёт только свой lease; `run_background` идёт через ту же дверь.
[CueRuntime.speak](../src/tg_agent_shell/cues/runtime.py) отличает свою отмену от отмены хода по
`Task.cancelling()`, а незакрытый review завершает существующей дверью SC-FAIL-005, которая же
снимает claim подагента. Окно отмены во время autoapproval закрыто в `RootSession._decide_or_show`.
Проверки: [test_cue_turn_e2e.py](../tests/e2e/test_cue_turn_e2e.py) с настоящими RootSession,
ProposalStore и CueRuntime — приход владельца во время подготовки и отмена перед autoapproval:
review и claims не остаются, Cue стоит в очереди, гейт снова открыт. Lease и остановка задачи —
в [test_reminder_flow.py](../tests/test_reminder_flow.py).

## 3. P2 — Проверять и завершать запись в правильном порядке

### 3.1. Согласовать commit и состояние review в памяти

**Факт.** [approve_proposal и decide_batch_item](../src/tg_agent_shell/proposals/use_cases.py)
удаляют review и меняют очередь до commit в [RootSession](../src/tg_agent_shell/session.py).
При искусственной ошибке commit переименование Card откатилось, но review и очередь исчезли.
[Autoapproval fallback](../src/tg_agent_shell/proposals/materialize.py) вернул id отсутствующего
предложения, вопреки комментарию о сохранении ручного review.

**Изменение.** Вычислять переход без разрушения текущего состояния, фиксировать БД и после
успешного commit применять переход к памяти. Свести ручной Save и autoapproval к одной границе
завершения операции. Отдельно сохранить предусмотренное завершение устаревшего предложения.

**Готово:** ошибка записи или commit откатывает данные и оставляет согласованное состояние
очереди; обещанный ручной review можно показать. Проверены оба пути Save, очередь из нескольких
предложений, повторное нажатие и отказ по устаревшей ревизии. Уже сохранённые элементы стоят,
неуспешный элемент не выдаётся за сохранённый. Основание: PR-FAIL-014, PR-AUTO-026, PR-STALE-012.

**Сделано.** `approve_proposal` стал границей завершения операции для обоих путей Save: применяет,
фиксирует БД сам и снимает review только после успешного commit; ошибка — rollback, review стоит,
экран отвечаем. Устаревшая ревизия по-прежнему завершает review намеренно. Лишние `session.commit()`
в [handlers](../src/tg_agent_shell/proposals/telegram/handlers.py) убраны, а fallback autoapproval
больше не выдаёт id отсутствующего предложения: review жив — показывается, завершён отказом —
очередь двигается как при неуспешном ручном Save. Проверки в
[test_proposals.py](../tests/test_proposals.py).

### 3.2. Отклонять некорректный Request до review

**Факт.** [normalize_card_query](../src/safwa/features/cards/api.py) ищет ai_cards как подстроку,
а SELECT id — в любом месте SQL. Следующий Request удалось сохранить, хотя внешний результат
не содержит id:

```sql
WITH c AS (SELECT id FROM ai_cards)
SELECT 1 AS amount FROM c
```

**Изменение.** Поверх исправленной границы из раздела 1 проверять компиляцию SQL и колонки
внешнего результата до создания review и при сохранении через use cases. Проверка должна
работать и на пустом результате; фактические значения id проверяются при исполнении.
Сохранить повторную проверку при каждом запуске и согласованную семантику выдачи Cards.

**Готово:** отсутствующий внешний id, синтаксическая ошибка и обход проверки источника не создают
ни review, ни Request; корректные запросы, порядок, устранение повторов и пустая выдача работают.
Не переносить ограничения размера ответа модели на пользовательский список Requests.
Основание: SR-SQL-004, SR-SQL-005, SR-AI-007, SR-RUN-006.

**Сделано.** `normalize_card_query` спрашивает не текст, а сам statement: `ai_cards` берётся из
списка прочитанных views исправленного сканера, колонка `id` — из компиляции
`SELECT * FROM (…) LIMIT 0`, которая работает и на пустом результате. Функция стала async и берёт
сессию; повторная проверка при каждом запуске сохранена, мёртвая проверка строк в `request_cards`
удалена. Фикстура `sessions` теперь создаёт `ai_*` views, поэтому тестовая база — форма production.
Проверки: [test_saved_requests.py](../tests/test_saved_requests.py) и
[test_saved_requests_e2e.py](../tests/e2e/test_saved_requests_e2e.py) — отсутствующий внешний id,
некомпилируемый запрос и обход проверки источника не создают ни review, ни Request.

## 5. P2 — Привести проверки к заявленным гарантиям

### 5.1. Использовать ту же сборку в production и E2E

**Факт.** [E2E provider](../tests/e2e/conftest.py) сам добавляет route и завершающий ответ,
а harness собирает читателей с полным ALLOWED_VIEWS иначе, чем production.

**Изменение.** Использовать общую сборку из раздела 4 с заменёнными сетевыми зависимостями.
Тесты маршрутизации и полного хода должны явно задавать каждый ответ провайдера и падать на
лишнем или отсутствующем вызове. Синтетические переходы не должны исправлять проверяемый сценарий.

**Готово:** реальные декларации определяют инструменты и views каждого читателя в обоих режимах;
тест обнаруживает чужую view, пропущенный route, лишний вызов и отсутствие финального ответа.
Нижние тесты фич остаются короткими и не обязаны каждый раз проверять весь диалог.

**Сделано — читатели.** `E2EHarness.subagent(name)` связывает подагента через
`AgentSpec.bind` и `AgentContext`, поэтому промпт, views, read tools и часы приходят из
декларации фичи, а заменена только Telethon; Advisor читает через `runner().scoped(ADVISOR_VIEWS)`,
helper — через `scoped(spec.views)`, как в [main.py](../src/safwa/bootstrap/main.py). Собранные
вручную подагенты в [test_subagent_e2e.py](../tests/e2e/test_subagent_e2e.py) удалены. Чужую view
ловит новый `test_ag_read_027_each_reader_reaches_only_the_views_its_own_list_names`: один и тот же
`SELECT` по `ai_card_events` читает только Diary, Advisor и workspace_mutator отвергнуты — без
скоупинга тест падает. Общая сборка раздела 4 при этом не понадобилась: декларации уже есть.

**Сделано — скрипты.** `ScriptedProvider` больше не вставляет ничего: один ответ на один запрос,
по порядку, а запрос, на который скрипта нет, валит тест. Синтетические `route` и финальный ответ
Advisor выписаны в 72 тестах; счётчики вызовов и индексы `provider.calls` приведены к тому, что
приложение действительно делает — раньше они не считали то, что вставлял сам harness. Что harness
ничего не чинит, проверяет
`test_a_script_that_leaves_a_step_out_fails_rather_than_being_repaired`
в [test_subagent_e2e.py](../tests/e2e/test_subagent_e2e.py): пропущенный `route` и пропущенное
последнее слово Advisor оба падают. Нижние тесты фич не тронуты.

## 6. P2 — Упростить поиск точек изменения фичи

Принято из второго аудита с сохранением явного ограничения читателей.

- Дополнить существующую диагностику картой «фича → исходники → BRD → тесты». Разбор ID и цитат
  переиспользовать из [brd_ids](../tests/brd_ids.py) и [traceability](../tests/test_brd_traceability.py),

- Рядом показывать опубликованные views и их читателей. Неизвестная view у читателя — ошибка;

## Какие предложения второго аудита приняты частично или отложены

| Предложение | Решение и причина |
|---|---|
| Автоматически расширять ADVISOR_VIEWS или хранить читателей в SqlView | Не принято: явные права читателя полезны, 10 опубликованных views и 9 у Advisor сейчас намеренны. Приняты диагностика и честное описание подключения. |
| Заменить буквы правил новыми ключами | Приняты понятные имена и области правил; старые ссылки сохраняются. Пропущенные буквы сами по себе не дефект. |
| Добавить shell ports.py и отдельный документ контракта | Принят единый обозримый контракт; новый слой протоколов и новый файл не обязательны, существующих типов и раздела AGENT_ARCH может хватить. |
| Удалить весь POLISHING немедленно | Принято сокращение после переноса уникальных решений и обновления ссылок. CLAUDE уже не требует читать его каждой сессии. |
| Сделать все dataclass runtime неизменяемыми | Не принято без анализа роли состояния. Исключение из C/D надо объяснить; аккумулятор не становится проще от обязательной immutable-копии на каждом шаге. |
| Делить Cards на три файла по 250–300 строк | Принято выделение ответственности, не заранее выбранное число файлов и строк. |
| Удалить trailing space из PERSONA отдельным исправлением | Отложено до изменения этого промпта: косметика меняет snapshot, но сама по себе не исправляет нестабильность prefix между ходами. |
| Считать граф импортов и ссылки BRD доказательством всей архитектуры | Не принято: воспроизведения разделов 1–3 и пробел Rule K прошли зелёные проверки. |

## Проверка при выполнении

Для каждого исправления исполнения сначала добавить воспроизведение, падающее на исходном коде.
Использовать временную или in-memory SQLite и вымышленные данные; гонки проверять управляемыми
событиями. После правки запускать затронутые тесты, а после изменения исполнения или общей сборки —
полный набор. Для чистой правки документации достаточно проверки документов.

```powershell
rtk proxy uv run pytest -q
rtk proxy uv run ruff check .
rtk proxy uv run python scripts/architecture_metrics.py
rtk proxy uv run pytest tests/test_docs.py -q
rtk proxy uv run pytest --brd=AG-READ-027 -q
```

Live Telegram остаётся отдельным явным запуском. Завершение пункта фиксировать по его критерию
готовности; зелёный общий прогон не заменяет проверку описанного перехода или контракта.
