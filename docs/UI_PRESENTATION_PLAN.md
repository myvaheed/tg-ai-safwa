# План улучшения оформления экранов Safwa

Дата аудита и реализации: 18 октября 2026. Подписи, Markdown в свободных полях и разделение текстовых блоков реализованы; отдельные расширения перечислены ниже.
Основание: чтение документации, экранов, общего вывода Telegram и UI-тестов. Визуальная проверка в живом Telegram в этот аудит не входила.

## Цель и принятые допущения

Подписи полей должны отличаться от значений: курсивная подпись вместе с двоеточием, затем обычное значение. Свободный текст должен показывать поддерживаемый Markdown. Заголовки экранов и разделов остаются жирными. Названия сущностей, даты, статусы, технические выражения и надписи кнопок остаются буквальным текстом.

Работа относится к представлению данных: исходные тексты сохраняются в прежнем виде, форматирование выполняется при показе. Локализация интерфейса и перестройка навигации в это предложение не входят.

## Предлагаемый вид Card

**Card**

*Kind:* ⭐️ Action  
*Title:* **Подготовить релиз**  
*Parents:* Запустить продукт  
*Stage:* Today

*Note:*

Сначала **проверить оплату**, затем пройти сценарий `checkout`.

*Schedule:* Сегодня до 18:00  
*Priority:* High  
*Categories:* 💰 Work  
*Energy:* 🧠 Cognitive

В настоящем экране названия связанных объектов остаются действующими ссылками. Пример показывает типографику полного экрана; компактный сохраняет свой текущий набор полей. Пустое значение отображается как «—», существующие предупреждения о недостающих Values сохраняются.

## Этап 1 — различимые подписи

1. Применить курсив к подписи и двоеточию во всех строках вида «поле: значение», включая общие экраны ввода и review. Значения, ссылки и выделение изменений сохранить.
2. Начать с общего обзора Card: он покрывает несколько вариантов экрана и ручное создание. Затем пройти остальные строки матрицы.
3. Если повторение оправдывает общий помощник, добавить только небольшое форматирование подписи в существующий Telegram-слой. Сущности и их поля продолжают принадлежать своим модулям; реестр схем экранов не нужен.

Проверка: у Kind, Categories, Parents и остальных подписей есть курсив; сами значения не получают его автоматически. Проверить компактную и полную Card, Goal с несколькими родителями, архив, создание, настройки и review. Адаптировать существующие проверки HTML, сохранив все поведенческие проверки и сценарии.

## Этап 2 — Markdown в содержимом

1. Использовать существующий преобразователь для Note, Blocked description, Description, текста Diary, инструкции Reminder, About me, Advisor instructions, Success criteria и свободных текстов Retro analysis.
2. Зафиксировать небольшой поддерживаемый набор: жирный, курсив, зачёркивание, встроенный код, блок кода, переносы и текстовые списки. Это соответствует существующему преобразователю; отдельные синтаксисы заголовков, таблиц и checkbox он сейчас не преобразует.
3. Внутренние ссылки на сущности сохраняются через существующее разрешение ссылок и адрес экрана. Внешний синтаксис Markdown-ссылок текущий преобразователь также не превращает в HTML-ссылки: его расширение выделить отдельной задачей, если нужна такая поддержка. Обычные URL сохранять в тексте.
4. Форматировать каждое свободное поле до сборки экрана. Сначала преобразование Markdown с экранированием, затем разрешение внутренних ссылок. Не передавать готовый экран повторно в преобразователь: там уже есть HTML, ссылки и иногда rich-таблицы.
5. Применять те же правила в ручных черновиках, чтобы Note и Description выглядели так же после сохранения. Если черновику требуется разрешение внутренних ссылок, оно должно выполняться с корректным адресом возврата в этот черновик.
6. Сохранить исходный текст в редакторе. Подсказку о Markdown показывать только для свободных полей. Названия, расписания, SQL, часы, timezone и прочие служебные значения показывать буквально.

Проверка: каждый тип свободного поля показывает форматирование; HTML-символы не превращаются в разметку; русский текст и emoji сохраняются. Внутренняя ссылка среди выделенного текста открывает объект и возвращает на исходный экран. Удалённая цель ссылки оставляет читаемые слова. Проверить сохранённый объект и ручной черновик.

Дополнительный обязательный случай: ссылка, записанная внутри встроенного кода или блока кода, остаётся примером текста. Сейчас преобразователь и разрешение ссылок выполняют независимые проходы, поэтому этот случай нужно закрепить проверкой при их совместном использовании.

## Этап 3 — ритм, длинные тексты и особые экраны

1. Короткие поля оставить компактными строками. Note, Description, About me, Advisor instructions и Success criteria показывать под своей подписью, отделяя от следующих полей пустой строкой. Не добавлять отдельный эмодзи каждому полю.
2. В Profile отделить два текстовых блока от настроек, в Reminder — время от инструкции и служебной подсказки, в Request — описание от результатов. В списках сохранить текущую сортировку, фильтры и число элементов на странице.
3. В review оставить исходный Markdown видимым при сравнении: жирный и зачёркивание принадлежат механизму изменений. Это позволяет видеть в том числе изменение только разметки. Не добавлять вторую копию текста с предпросмотром на каждый review. В этой итерации одинаковый Markdown-предпросмотр review и обычного экрана не обещается.
4. Сохранить существующее сворачивание длинных полей review. Проверить заметки около границы длины Telegram: сворачивание само по себе не сокращает отправляемый текст. Обычные экраны с кнопками сейчас идут отдельным путём от автоматически разбиваемой прозы; если проверка выявит переполнение, вынести постраничный просмотр длинного текста с возвратом в отдельную задачу до объявления поддержки таких длин.
5. Проверить Memory отдельно: общий текст используется и для советника. Улучшать его вид только в Telegram-адаптере, если это можно сделать без изменения читаемого содержимого и нового парсера текстовой сводки. Это необязательная часть данного плана.
6. Просмотреть репрезентативные экраны в Telegram на узкой ширине: полный Card, Note со списком и кодом, Check, Value, Profile, Diary, review, Dashboard и Sprint plan. Автоматические проверки строк не подтверждают визуальное качество.

Проверка: подпись и значение легко различаются; текстовые блоки не сливаются; длинный текст не исчезает молча; кнопки и возврат работают как раньше; rich-таблицы сохраняются.

## Порядок выполнения и готовность

Рекомендуемый первый пакет: этап 1 целиком и Markdown для Card, Check, Value, Tag. Он закрывает исходную проблему и даёт образец для остальных экранов. Второй пакет: оставшиеся свободные поля из этапа 2. Третий: отступы, особые экраны и визуальная проверка из этапа 3. Изменения Memory, внешние Markdown-ссылки и просмотр текста сверх лимита — отдельно обозначенные расширения.

Для реализации дополнить существующие сценарии экранов правилами подписей и Markdown, затем добавить проверки реального рендеринга и навигации в существующие UI-тесты. Тесты не удалять и не заменять без решения владельца. Уточнять ожидаемую разметку в текущих утверждениях допустимо при сохранении проверяемого поведения.

Перед завершением каждого пакета выполнить проверки из README: `rtk uv run ruff check .` и `rtk uv run pytest -q -n auto`. Целевые проверки должны охватить Card, Check, Value, Tag, Profile, Reminder, Request, Diary, Sprint/Retro, цитирование, review, редактор и оба способа вывода таблиц. Документацию проверяет существующий `tests/test_docs.py`.

Готовность исходного запроса: подписи полей последовательно курсивные, согласованные свободные поля показывают заявленный Markdown, исходник остаётся доступен для редактирования, ссылки и проверка изменений сохраняют своё назначение. Визуальная проверка в живом Telegram остаётся отдельной проверкой: автоматические UI-тесты подтверждают текст и действия, но не внешний вид клиента Telegram.

## Результат реализации

- Курсивные подписи добавлены в Card, Check, Value, Tag, Profile, Hooks, Planning, Sprint plan, Retro, Life settings, Status, общие редакторы и review. Таблицы Dashboard и Sprint plan сохранены.
- Markdown включён в согласованных свободных полях, включая Diary instruction профиля и причину блокировки в списке Sprint. Исходный текст в данных не меняется.
- Свободные поля выделены в отдельные блоки. В Profile текстовые поля сгруппированы перед короткими настройками и показываются по одному разу.
- Ручные черновики показывают тот же Markdown. Упоминания сущностей в них читаются без ссылок: переход на другой экран завершает несохранённый черновик по существующему правилу.
- В обычном тексте ссылки сохраняют переход и возврат; внутри кода они остаются буквальными примерами. Review сохраняет исходный Markdown и выделение изменений.
- Добавлены сценарии SC-LABEL-015 и SC-TEXT-016 и проверки экранов в `tests/test_screen_formatting.py`. Прежние UI-проверки обновлены под новую разметку без удаления сценариев.
- Memory, внешние Markdown-ссылки и отдельный просмотр текста сверх лимита сообщений не включены в эту реализацию. Полный Markdown с таблицами, checkbox и заголовками также не заявляется.
