# Очистка всего набора за 10 батчей

Единица работы — крупная область поведения со всеми уровнями тестов. Каждый батч заканчивается
одним проверенным изменением набора. Отдельный тест не требует отдельного батча, прогона
или согласования. Предварительная очистка шести тестов считается пилотом, а не одним из десяти батчей.

## Распределение и границы

[test_batches.json](test_batches.json) назначает каждый из 180 существующих тестовых файлов
ровно одному батчу. Это ответственность за разбор, а не запрет читать или использовать
покрытие других батчей. Общие E2E-файлы рассматриваются целиком в назначенном батче,
их проверки используются как оставшееся покрытие во всех остальных.

| Батч | Область | Файлов | Случаев при подготовке пайплайна |
|---|---|---:|---:|
| 1 | Инструменты покрытия, инфраструктура, архитектура и документация | 14 | 944 |
| 2 | Runtime, ходы, доступ и hooks | 19 | 291 |
| 3 | Предложения, подготовка, Save/Discard | 15 | 186 |
| 4 | Cards, иерархия, завершение, порядок, учёт времени и усилий | 18 | 292 |
| 5 | Checks, Values, Tags, связи и reviews | 23 | 279 |
| 6 | Вычисление расписаний, календарь и границы | 10 | 215 |
| 7 | Reminders, условия, запуск и доставка | 15 | 287 |
| 8 | Diary, memory, retro и heavy analyzer | 13 | 151 |
| 9 | Planning, Home, Profile, Thoughts, Blueprint, Compass, onboarding | 28 | 356 |
| 10 | История, поиск, provider, голос, privacy; итоговая сверка | 25 | 325 |
| Всего | Весь текущий набор | 180 | 3326 |

В батче 1 сотни случаев генерируют несколько структурных проверок: оценивать их общие
правила и выбор входов, а не писать сотни индивидуальных обоснований. Размер батча отражает
работу по разбору поведения, а не только количество параметров pytest.
Новые тестовые файлы сразу назначать одному из этих же десяти батчей. При удалении целого
файла убирать его из текущего распределения и записывать удаление в журнал; история Git
сохраняет исходное распределение. Незавершённую область не переносить в выдуманный батч 11.

## Батч 1: подготовка и исходная точка

1. Подключить pytest-cov и coverage.py. Снимать строки, ветви, контексты тестов и subprocess;
   измерять все пакеты src и приложения examples. Ничего не исключать из измерения ради цифры.
2. Собрать полный список pytest ID, параметров, BRD-ссылок и opt-in-маркеров командой inventory.
   Она проверяет отсутствие неназначенных, пропавших и дважды назначенных файлов.
3. Перепроверить пилот: временно вернуть шесть удалённых тестов из исходной ревизии,
   сохранить первоначальный вариант проверенного теста в test_summary.py, снять исходный
   snapshot, затем вернуть текущее состояние тестов и сравнить покрытие. Приложение и настройки
   при этом не менять. Каждую обнаруженную потерю разобрать до закрытия батча 1.
4. Разобрать все структурные проверки батча 1 по [критериям](TEST_QUALITY.md), выполнить
   общий цикл ниже и сохранить принятый результат как исходную точку для батча 2.

Пилот проверен в батче 1 по исходному замеру с возвращёнными шестью тестами.
Один тест восстановлен после обнаружения уникальной ветви; пять удалений подтверждены.
Принятая точка для батча 2 — batch01-final; подробности находятся в журнале очистки.

## Один цикл для каждого батча

1. **Общий вход.** Прочитать сценарии области, реализацию и тесты всех её уровней. Использовать
   snapshot предыдущего принятого батча; один раз снять свежий замер, если он устарел.
2. **Групповая оценка.** Разделить проверки на семейства по правилу и классу ошибки.
   Для каждого семейства записать решение: сохранить, сократить параметры, усилить или удалить
   перекрытые проверки. Сначала сопоставить условия и assertions; контексты покрытия помогают
   найти пересечения, но не доказывают дублирование. Приоритет — повторные happy paths,
   внутренние флаги, проверки моков и эквивалентные параметры.
   Просмотреть также исходно непокрытые ветви своей области: отделить нужное непроверенное
   поведение от кандидатов в ненужный код. Отсутствие выполнения не доказывает ненужность.
3. **Одно изменение.** Применить все обоснованные решения батча вместе. Не запускать полный
   набор после удаления каждого теста. Спорный тест оставить с указанной причиной внутри
   текущего батча; это завершённое решение, а не скрытый перенос работы.
4. **Проверка области.** Запустить затронутые доменные/UI/shell/E2E-тесты и BRD traceability.
   Mutation-пробы делать только для спорного перекрытия или существенного риска, по семейству,
   без обязательного отдельного запуска на каждый удалённый тест.
5. **Один общий контроль.** Снять полный snapshot после батча, выполнить compare с предыдущим
   принятым snapshot и с начальной точкой всей сессии. Запустить Ruff и архитектурный сканер.
   Полный snapshot уже является полным прогоном pytest; отдельно повторять тот же прогон не нужно.
6. **Разбор потерь и принятие.** Нужное поведение — вернуть/усилить проверку. Подтверждённо
   ненужный код — отдельное явно описанное изменение в этом же батче; после него заново снять
   исходный и итоговый замеры на одинаковой версии приложения. Изменение исходников делает
   прямое сравнение номеров строк недействительным, compare его отвергает.
   Повторять контроль только после исправлений или для выяснения нестабильной потери.

Потери сравниваются по множествам строк и переходов, не по округлённому проценту.
Не объяснённая потеря блокирует принятие батча. Нулевые потери не доказывают сохранение
assertions: журнал сопоставляет также проверяемые результаты. Общие fixtures могут попадать
в setup первого использовавшего их теста; потеря контекста не равна потере поведения.
Opt-in-тесты входят в инвентаризацию и ручной разбор, но их поведение не объявляется
проверенным локальным покрытием. Live-запуски остаются отдельными, явно разрешёнными.

## Команды и результаты

[scripts/test_audit.py](../scripts/test_audit.py) предоставляет три операции:

```powershell
rtk proxy uv run python scripts/test_audit.py inventory
rtk proxy uv run python scripts/test_audit.py snapshot baseline
rtk proxy uv run python scripts/test_audit.py snapshot batch01
rtk proxy uv run python scripts/test_audit.py compare .test-audit/baseline .test-audit/batch01
rtk proxy uv run ruff check .
rtk proxy uv run python scripts/architecture_metrics.py
```

Каждый snapshot сохраняет компактный coverage JSON, интерактивный HTML, базу coverage с контекстами,
JUnit-результат и контрольные суммы исходников, настроек и зависимостей в .test-audit.
Прогон с покрытием использует четыре процесса: контексты и инструментирование subprocess
требуют больше ресурсов, чем обычный pytest; число процессов не зависит от числа ядер машины.
Существующий snapshot не перезаписывается; после исправления использовать новое имя.
Неуспешный прогон не получает признака завершённого snapshot и не принимается compare.
Compare записывает losses.json в каталог итогового snapshot и возвращает ненулевой код
при потерях; подробности называют строки, ветви и прежние контексты потерянных строк.
Отчёты локальные и игнорируются Git. Решения и численные итоги сохранять в [журнале](TEST_CLEANUP.md).
После изменения окружения исходный и итоговый snapshot снять заново.

## Отчёт и критерий завершения

На батч — одна запись: охваченные файлы/семейства, количество случаев до/после, решения,
удалённые pytest ID или точные группы параметров → оставшиеся проверки и проверяемые результаты,
потери покрытия и их объяснения, проверки, сознательно оставленные спорные тесты.
Для сохраняемого семейства достаточно общего основания; индивидуальные карточки всех тестов не нужны.

После батча 10 у всех файлов должен быть завершён разбор, у каждого удаления — оставшееся
поведение или подтверждённое удаление ненужной функции продукта, у каждой потери — решение.
Сверить исходный и текущий список ID, в том числе opt-in; сверить суммарные удаления и добавления.
Полный набор, Ruff и архитектурные ограничения проходят. Нет нормы «удалить N процентов»:
за десять батчей завершается аудит всего набора, сколько проверок останется — результат анализа.
