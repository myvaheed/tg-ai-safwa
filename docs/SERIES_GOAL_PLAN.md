# План: условия на ответы и цель серии, этап 2

Дата: 23 октября 2026. Продолжение [этапа 1](HABIT_TRACKERS_PLAN.md) на ветке
claude/habit-trackers. Основание: §6 и §8 [обзора напоминаний и трекинга](REMINDERS_TRACKING_REVIEW.md).

Оформление то же, что в этапе 1: моноширинным шрифтом — только имена, которые уже есть в коде;
имена, которые план вводит, — *курсивом*. Тексты промптов ниже — черновики на согласование.

## Цель

Владелец говорит: «Скажи, когда я помедитирую 30 утр подряд». Safwa ставит Reminder на ответы
трекера «Помедитировал?». Он срабатывает один раз, на 30-м Passed подряд, и удаляет себя. Ряд рвёт
только явный Missed: утро без ответа просто выпадает, а открытый вопрос переезжает на следующее утро.
Смена часа медитации ряд не обнуляет: цель живёт в Reminder и считает всю историю серии, а не
ревизию Schedule.

Прежде этого Reminder на ответы должны считать правильно: когда ответы сохранены вместе, когда
удалён первый экземпляр серии, когда Value перешла к следующему экземпляру.

Новой сущности нет, схема БД не меняется: условие хранится в JSON-колонке `Reminder.condition`.

## Что сломано сейчас

| Случай из §8.2 | Причина в коде | Батч |
|---|---|---|
| Done одной Action отвечает на 3 Checks, условие «каждые 3 ответа»: 3 одинаковые Cue | Хук идёт по каждому ответу, а `count_now` считает итог после commit: все три видят 3 | 1 |
| То же с 4 Checks: ни одной Cue | Итог 4 не кратен 3 | 1 |
| Условие на Check #N, удалён первый экземпляр #N: серия больше не находится | SELECT ищет `series_id` через строку #N | 2 |
| В серии 2 Passed, новая ревизия разрешает ещё 2 ответа: порог «3 Passed всего» отклонён как недостижимый | Проверка достижимости брала лимит последней ревизии, а `count_now` считает всю историю | 2 |
| SELECT по `direct_values` находит только Pending-экземпляр, условие молчит | Value переходит к новому экземпляру, а SELECT выбирает экземпляры, а не серии | 2 |
| SELECT с фильтром по Passed выкидывает Missed и искажает «подряд» | То же | 2 |

## Батч 1 — счёт по месту ответа (сделан)

Критерий успеха: тест с условием «every 3 answers» и Done Card, на которой 3 или 4 Checks. Сейчас
3 Cue и 0 Cue, после батча — по одной.

- `count_now` считает не итог после commit, а историю до этого ответа включительно. Ответы
  упорядочены по `resolved_at` и id, у Done — по `completed_at` и id.
- Ответ срабатывает, когда его место кратно порогу. «Подряд» — ряд, который кончается этим
  ответом.
- Счётчик не хранится, пакет не собирается: каждый ответ проверяется один раз, своим событием.
- Исправленный ответ по-прежнему ничего не запускает.
- RM-COND-032: строка о том, что ответы, сохранённые вместе, считаются по одному в порядке
  сохранения: 3 и 4 ответа одним Done дают одну Cue, на третьем.
- Промпты не меняются.

## Батч 2 — сначала серии, потом их ответы (сделан)

Критерий успеха: тесты на три случая §8.2 падают до батча и проходят после: удалённый первый
экземпляр, Value на Pending-экземпляре, порог при новой ревизии.

- Код берёт серии найденных экземпляров (`series_id` в `ai_checks`, серия Card в `ai_cards`) и
  считает всю их историю. SELECT выбирает, какие привычки, а не какие ответы.
- Один Check или одна Action (D7): код сам пишет SELECT по id серии, например
  `SELECT id FROM ai_checks WHERE series_id = 12`. Id серии не меняется, когда удаляют
  экземпляры. Вторая мини-сессия для такого условия не запускается.
- Группы — по Tag, по Value, «any Check», «Checks of Action #7» — по-прежнему пишет вторая
  мини-сессия, но счёт идёт через тот же выбор серий.
- `never_reached` (D5): ответы, которые счётчик уже видит, плюс оставшиеся по текущей ревизии.
  Отказ называет причину: «Check #7 does not repeat, so a count of 3 never comes.» или
  «Check #7 counts 2 now and has 2 answers left, so a count of 5 never comes.»
- Промпт второй мини-сессии: убрать три строки, которые теперь делает код (черновик ниже).
- Сценарии: RM-COND-030 — один Check или одна Action по #id получают SELECT от кода;
  RM-COND-033 — найденные экземпляры берутся сериями, поэтому удаление первого экземпляра и
  переход Value их не теряют; RM-COND-034 — область счёта.

## Батч 3 — открытый экземпляр на текущем периоде (D1, сделан)

Сейчас открытый экземпляр держит своё время, пока на него не ответят. Ответ на пятый день
записывается за четвёртый, и следующий экземпляр открывается только на шестой. В ветке
reminders-as-checks это уже сделано в v9.221 (SCH-PERIOD-031); батч переносит эту часть сюда.

Критерий успеха: тест на ежедневный Check в 07:00.

1. Passed в первые три утра.
2. Четвёртое утро без ответа. В начале пятого дня тот же экземпляр переезжает на 07:00 пятого
   дня; четвёртый день остаётся без ответа.
3. Passed в 09:00 пятого дня считается за пятый день, следующий экземпляр — на шестой.
4. Passed на шестой день: 5 Passed подряд, Missed нет.

- Хук *schedules.period* на тике и при старте переводит открытый экземпляр повторяемого Schedule
  на период, в котором сейчас время. Период, который он покидает, остаётся без ответа.
- `prepare_occurrence`: ответ считается за период, в котором он дан. Сейчас так только у квоты.
- Период момента на днях — от начала его дня до начала дня следующего момента. Период интервала
  — до следующего момента. Период квоты — её день, неделя или месяц.
- Отличие от ветки: там интервал обходил тихие часы из своего `timing`. Здесь Don't disturb живёт
  в Profile и на Schedule Action и Check не действует (этап 1, D1), поэтому обход тихих часов не
  переносится.
- Сценарий SCH-PERIOD-031 переносится с тем же номером, с примером ряда выше. SCH-INTERVAL-009 и
  строка SCH-REMIND-020 об открытом экземпляре меняются так же, как там.
- Отличие от ветки в Remind: здесь Remind — Reminder с якорем на моменте экземпляра. Переезд
  двигает и якорь, а следующий звонок оставляет. Иначе переименование увидело бы другой timing,
  пересчитало Reminder, и интервальный Remind прозвенел бы за прошедший момент ещё раз.
- `answer_run`, Repeated Missed и счёт условий не меняются: ряд рвёт только явный Missed.

## Батч 4 — «после N» один раз и счёт сейчас (D3, D4, сделан)

Критерий успеха: тест на «after 3 Passed in a row of Check #N». На третьем Passed — одна Cue со
строкой `LAST_FIRE`, Reminder удалён, на шестом — ничего. Подготовка отказывает, если порог уже
пройден.

- `Condition` и `ConditionInput` получают *once*.
- С *once* условие срабатывает, когда место ответа равно порогу. Reminder удаляется в той же
  транзакции, что пишет Cue, и Cue говорит `LAST_FIRE`, как у последнего срабатывания повтора.
- `describe`: «after 30 Passed in a row of Check #7» вместо «every 30 …».
- Экран Reminder и /reminders: к строке «🔎 Finds now» добавляется счёт сейчас, например
  ««Meditated?». 12 Passed in a row now.»
- Подготовка: если *once*, а счёт уже не меньше порога, — отказ с формами RM-UNCLEAR-028 и
  словами «Check #7 already has 34 Passed in a row, so 'after 30' is already past.» Не «never
  comes»: после Missed ряд начнётся заново и снова может дойти до 30.
- Промпты: поле *once*, пример «after» в `REMINDER_WHEN_PROMPT`, описание `ai_reminders`,
  онбординг (черновики ниже).
- Новый сценарий *RM-COND-040* «A Reminder after N answers fires once».

## Батч 6 — сабагент reminder

Замер батча 5 показал, что mutator не справляется: его контекст раздут Sprint, Values и правилами
всех сущностей. Владелец решил отдать Reminder и Remind своему сабагенту, а mutator оставить
только про сущности.

- Сабагент `reminder` с инструментами `reminder`, `remind` и `remove` читает Reminders, Checks,
  Cards, Tags и Values и не получает состояния рабочего пространства. Инструмента, который
  создаёт Check или Action, у него нет (`RM-AGENT-041`).
- `remind` — Remind на существующей Action, Goal или Check. Его изменение — обновление этого item
  с одним Remind, так что готовит и применяет его фича item. У `action`, `goal` и `check` поля
  `remind` больше нет: новый item с Remind — два экрана, сначала item, после его Save — Remind.
- Описание `answer` в мини-сессии говорит passed (yes) и missed (no).

## Батч 7 — что считают, решают items (D8)

Замер батча 6 показал «every 30 Done of Check #3»: модель выбирала одно значение `answer`, которое
говорило сразу две вещи — Check это или Action и какой ответ, — а код выводил вид item из ответа.
Правила вида «Only an Action is Done» латали этот изъян и не помогали.

- **Модель называет только полярность:** `answer` — yes, no или any. yes — это Passed у Check и
  Done у Action, no — Missed у Check, any — любой ответ.
- **Вид item решают items:** для одного item — слово в «Check #12» или «Action #7», для остальных —
  поле `returns` у терминала второй мини-сессии, рядом с SELECT, который его читает. `Condition` хранит `kind`
  (check или action) и `answer`; экран говорит Passed, Missed, answers или Done по виду.
- **У Action один ответ — Done:** он хранится как yes, «подряд» у Action — это все Done, Missed у
  Action отклоняется с формами ответа.
- **Голый #id** («#14») возвращается мини-сессии: «Name each #id as 'Check #14' or 'Action #14' in
  items.» «Check #14 «Название»» код узнаёт сам.
- **Промпт `reminder`** (П8): слова владельца как есть, с item в виде «Check #12» или «Action #7»;
  примеры «every …», правило «after» и правило про Done ушли.

Поле там названо `returns`, а не `kind`: у `ai_cards` в том же промпте есть колонка `kind`
(goal или action).

Сокращённый замер на каждую правку — фразы `goal`, поток цели серии, Remind и «Also track», 47
кейсов. 46 фраз о времени по часам гоняются в конце батча: их меняет только часть промпта
мини-сессии о часах.

## Батч 8 — слова владельца в `when`, Remind и удаление (П10–П12)

- **П10, описание поля `when`:** «The user's own words for when, in their language, with each Check

## Батч 9 — У1: items только по #id (сделан)

Счёт в Condition уже прост: yes, no или any, count, in_row для yes и no, once. Сложны items:
группа словами («Actions tagged sport», «Checks ценности Health») становится SQL второй
мини-сессии, и этот SELECT выполняется при каждом ответе. Замер батча 8: список «Action #1,
Action #2» и выдуманный «Check #5» уходят во вторую мини-сессию, и та пишет SELECT, который
ничего не находит.

**Решение.** Items — только Checks или только Actions, каждый по #id. Группу сабагент
разворачивает в список сам, через `query_data`, когда ставит Reminder. Вторая мини-сессия и SQL
уходят целиком.

**Критерий успеха.**
- В потоке цели серии нет провалов «SELECT ничего не нашёл» и «item не существует».
- Слепые фразы с группой возвращаются с отказом, а не с чужим SELECT.
- Полный набор зелёный; в `conditions.py` нет SQL.

### Схема

`Condition`: `items` (слова для экрана), `series` (корни серий: id, который остаётся при удалении
любой копии), `kind`, `answer`, `count`, `in_row`, `once`. Поля `sql` больше нет. Схема БД не
меняется: условие лежит в JSON.

### Код

- Items разбирает код: каждая ссылка — «Check #N» или «Action #N», с названием в кавычках или без,
  между ними только запятые, «и», «and», «&». Иначе — отказ сабагенту.
- Отказы (идут сабагенту с формами ответа, как сейчас):
  - группа или слова помимо #id: «Name each item by #id, as 'Check #1, Check #2'. Find a group's
    items with query_data.»;
  - Checks вместе с Actions: «Count Checks and Actions in separate Reminders.»;
  - #id, которого нет: «Check #5 does not exist.» Это П14, он входит сюда.
- Голый «#14» по-прежнему возвращается мини-сессии с NAME_THE_ID.
- Уходят: вторая мини-сессия с её промптом, схемой и терминалом, проверка SELECT как текста,
  выполнение SQL в `found_ids`, список Tags и Values для SELECT и параметр `names` у
  `resolve_schedule`.
- Разбор одного item становится разбором items в `(kind, series)`, `items_series`; `found_ids` — запрос ORM по
  корням серий. П13 не нужен: список #id и так идёт через код.

## Батч 10 — У2: условие полями в `reminder` (сделан)

Сейчас сабагент пересказывает слова владельца в `when`, а мини-сессия читает из пересказа items,
ответ, счёт, «подряд» и «один раз». Замер У1: на этом пути теряется «каждый раз» и `once`, а
мини-сессия меняет вид item («Check #1» стал `items='Action #1'`). Условие — это пять отдельных
полей без календарной арифметики; их может назвать сам сабагент, который видит слова владельца
и уже нашёл items.

**Решение.** У `reminder` появляется поле `condition` с полями `ConditionInput`: items, answer,
count, in_row, once. Reminder ставят по `when` или по `condition`, не по обоим. `when` остаётся
только для времени; мини-сессия читает только время.

**Критерий успеха.**
- В потоке цели серии нет провалов от пересказа: вид items, `once` и счёт — те, что в словах
  владельца.
- 20 фраз `goal` про ответы мини-сессия возвращает с `about=answers`, 4 фразы про время — как
  раньше.
- Remind и «Also track» не хуже; полный набор зелёный; в `resolve_schedule` нет условия.

### Код

- `ReminderToolInput`: поле `condition: ConditionInput | None`. `create_requires` — только
  `instruction`; валидатор: create требует `when` или `condition`, оба сразу — отказ. Update без
  обоих оставляет расписание, как сейчас.
- `ConditionInput` со своим валидатором (in_row без yes или no, голый #id, Missed у Actions)
  переезжает из мини-сессии в tool: эти ошибки сабагент получает сразу на вызове.
- Подготовка строит `Condition` из полей: `items_series`, затем `found_ids` и `never_reached`, как
  сейчас. Ошибки идут сабагенту своими кодами, без форм ответа:
  - items не по #id, двух видов или несуществующие — *condition_items*, подсказка ведёт к
    `query_data` (П17);
  - счёт, которого одна серия не достигнет, или «after N» уже пройдено — *count_never_reached*,
    подсказка — сказать владельцу.
- Мини-сессия: уходят терминал `set_condition`, блок примеров ответов и параметр `items_series` у
  `resolve_schedule`. Если в `when` всё же пришли ответы, она отвечает `not_clear_enough` с
  `about=answers`, и сабагент получает *when_counts_answers*: поставить `condition` вместо `when`.
  Это подстраховка ценой одной строки промпта.
- `unclear` оставляет только формы времени; формы ответа уходят: ни владелец, ни
  сабагент больше не пишут ответы словами для мини-сессии.
- Ложные docstring чинятся на месте: модуль `agent.py`, `proposal.py`, экран (`screen` ещё
  говорит «what its SELECT finds»), `conditions.py` («as the `when` session writes»).

## Тексты на согласование

Mutator не меняется: он передаёт слова владельца в `when` как есть.

**1. Промпт второй мини-сессии, батч 2.** Убрать три строки, которые теперь делает код. Ничего не
добавляется, мини-сессия групп читает на три строки меньше:

```text
A Check or an Action named by #id means its whole series: every copy of it.
'Check #12': SELECT id FROM ai_checks WHERE series_id = (SELECT series_id FROM ai_checks WHERE id = 12)
'Action #7': SELECT id FROM ai_cards WHERE series_id = (SELECT series_id FROM ai_cards WHERE id = 7)
```

**2. Поле *once* в `ConditionInput`, батч 4.** Одна строка описания поля:

```text
true for 'after N': it fires once, at N. false for 'every N'.
```

**3. `REMINDER_WHEN_PROMPT`, батч 4.** Пример «after» уже есть; он получает `once=true`. Без
этого «after 40» и «every 40» неразличимы:

```text
'after 40 Passed in a row of Check #7': items='Check #7', answer=passed, count=40, in_row=true, once=true.
```

**4. Описание `ai_reminders`, батч 4.** Строка о `condition`, чтобы Advisor читал *once*:

```text
- `condition` is JSON `{items, sql, answer, count, in_row, once}`: it fires each time the answers (passed | missed | answered | done) of the ids `sql` finds reach a multiple of `count`, or once at `count` when `once`; in a row when `in_row`; its `next_fire_at_local` is null
```

**5. Онбординг, батч 4.** Меняется строка о Reminder на ответы:

```text
- A Reminder on answers fires at every multiple of its count: 3, 6, 9. "After 30" fires once, at 30, and then deletes itself. A corrected answer fires nothing. Its words select the items again at every answer, so items made later count too, and deleting them leaves the Reminder. Its screen shows what they find now and the count now.
```

**6. Пример «after» в mutator, батч 5.** Откатан: ни одного «after» за 18 вызовов `reminder`.

**7. Промпт второй мини-сессии без ответов, батч 5.** Убраны колонки `status` и `stage`, строки их
значений и запрет фильтровать по ним: сессия групп не видит ответов и не фильтрует по ним.

**8. Два повтора, батч 5.** Убраны строка `REMINDER_WHEN_PROMPT` «items: the phrase's own words…»
(её говорит описание поля `items`) и строка промпта второй мини-сессии «Read ai_checks for answers of
Checks, ai_cards for Done of Actions.» (её говорит контекст сессии).

## Не входит

- Остановка трекера или закрытие Goal при достижении порога.
- Окно оценки: «напомнить в 07:00, отметить до 10:00» (§3 обзора, п. 4).
- Ряды по квотам: «3 недели подряд по 3 раза».
- Advisor сам предлагает цель серии в разговоре.
- Перенос экрана звонка, Delay и возврата экрана из ветки reminders-as-checks.

## Риски

- **Группа через #id.** «Checks of Action #7» по-прежнему ищет серию через строку #7: удаление
  первого экземпляра Action ломает такую группу.
- **Один трекер по тексту items.** Если модель напишет «#12» или «Check #12 «Название»», условие
  пойдёт через вторую мини-сессию. Счёт останется правильным, но удаление первого экземпляра снова
  сломает SELECT. Батч 5: так в 6 из 20 одиночных фраз без слова Check или Action; через mutator —
  ни разу.
